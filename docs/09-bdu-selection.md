# Порядок отбора угроз из БДУ ФСТЭК России

## 1. Общий подход

Перечень угроз в `registers/threats.csv` сформирован не путем механического копирования всех записей банка данных, а на основании архитектуры системы, объектов воздействия, возможных последствий и потенциала нарушителей.

Для каждой угрозы в реестре указан поисковый ключ `bdu_search_key`. Он используется при работе с актуальной версией банка данных угроз ФСТЭК России. Идентификатор записи БДУ фиксируется только после проверки полного описания угрозы, объектов воздействия, источника и условий реализации.

Такой порядок исключает ошибочное присвоение идентификатора угрозе только по сходству названия.

## 2. Последовательность отбора

1. Определить объект воздействия и нарушаемое свойство безопасности.
2. Установить возможный источник угрозы и доступные ему интерфейсы.
3. Сформулировать сценарий реализации угрозы применительно к архитектуре системы.
4. Выполнить поиск в БДУ по ключевым словам и типу объекта воздействия.
5. Проверить описание найденной записи, условия реализации и последствия.
6. Зафиксировать идентификатор и дату проверки в рабочей версии реестра.
7. При отсутствии точного соответствия оформить собственную формулировку угрозы со ссылкой на использованные исходные данные.

## 3. Критерии актуальности

Угроза признается актуальной, если одновременно выполняются следующие условия:

- в системе присутствует объект воздействия;
- существует источник угрозы с необходимыми возможностями;
- имеется достижимая точка входа или способ воздействия;
- реализация сценария может привести к установленным негативным последствиям;
- действующие или проектируемые меры защиты не исключают возможность реализации угрозы полностью.

Наличие записи в БДУ само по себе не является достаточным основанием для признания угрозы актуальной.

## 4. Фиксация результата

В рабочем комплекте рекомендуется использовать дополнительные поля:

| Поле | Назначение |
|---|---|
| `bdu_id` | Идентификатор подтвержденной записи БДУ |
| `bdu_title` | Наименование записи на дату проверки |
| `checked_at` | Дата проверки актуальной версии БДУ |
| `checked_by` | Исполнитель проверки |
| `applicability_note` | Обоснование применимости или неприменимости |

В публичном демонстрационном проекте идентификаторы не проставляются без проверки актуального содержимого БДУ. Это сделано намеренно: банк данных обновляется, а совпадение по названию не гарантирует совпадения условий реализации.

## 5. Пример обоснования

**Угроза:** эксплуатация уязвимости внешнего сервиса.

**Объект воздействия:** прикладное программное обеспечение и конфигурация внешнего API.

**Источник:** внешний нарушитель с сетевым доступом.

**Условия:** сервис опубликован в сети, обрабатывает недоверенные данные, в составе ПО может присутствовать уязвимый компонент.

**Последствия:** выполнение несанкционированных команд, изменение данных, нарушение доступности.

**Вывод:** угроза актуальна; требуется сопоставление с записью БДУ по признакам эксплуатации уязвимости сетевого сервиса, а не только по совпадению формулировки.
